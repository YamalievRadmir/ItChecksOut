# Аудит перед production — 12 ноября 2026

## Исправления

- Убраны System.err/printStackTrace и сообщения исключений из HTTP-ответов/Notification. Подробности остаются в серверном журнале и ErrorLog; недоступность ИИ не создаёт всплывающее уведомление.
- Все запросы бизнес-сущностей используют ShopRepositoryBase или явный shop-предикат. Добавлена проверка явного аргумента Shop. Неиспользуемый Query-by-Example запрещён вместо неограниченного чтения; пакетное удаление переведено на проверяемые операции.
- Глобальные журналы и пользователи доступны через SuperAdminService с hasRole(SUPER_ADMIN); локальные журналы используют shop-фильтр. DeliveryItemRepository отсутствует: строки доставки сохраняются каскадно через Delivery и проверяются ShopEntityListener.
- API /api/public/delivery-order выделен в stateless SecurityFilterChain. Браузерная сессия не авторизует интеграцию. Требуется X-Site-Order-Key, проверяемый constant-time сравнением; пустой/короткий ключ запрещает запросы. CSRF отключён только для этой цепочки, использующей явный секрет вместо cookie. Для Vaadin сохраняются штатные CSRF-защиты Spring/Vaadin.
- Демо-вход выключен по умолчанию. Демо-магазин помечен отдельно, вход его пользователей запрещён при выключенном демо, включая обычную форму логина.
- Новые и изменяемые пароли проверяются: минимум 12 символов, максимум 72 байта UTF-8; старые хеши требуют отдельной политики ротации.
- Убрана генерация plaintext-файла bootstrap-пароля. Новая установка требует APP_BOOTSTRAP_SUPER_ADMIN_PASSWORD. Пользовательские пароли сохраняются BCrypt.
- Cookie-only сессии, SameSite=Lax, HttpOnly; при обычном логине создаётся новая сессия без старых атрибутов. Корзина дополнительно очищается при смене пользователя.
- Общий бэкап разрешён только SUPER_ADMIN. Один Telegram-канал получает события только явно настроенного магазина app.telegram.shop-id; 0 выключает маршрутизацию.

## Запросы и целостность

- ProductRepository.findAllByShop: EntityGraph для shop. Коллекции alternativeProducts/recommendedAdditives и Product используют BatchSize(64), глобальный default_batch_fetch_size=64. Две коллекции не JOIN FETCH одновременно в списке товаров, чтобы не создавать декартово раздувание результата.
- SaleRepository: EntityGraph items + items.product для истории и расчёта себестоимости.
- Продажи, поставки, инвентаризация, приёмка партии, выполнение доставки и правка чеков транзакционны. Связанные Product/Customer загружаются через магазинные запросы; остатки блокируются pessimistic write в стабильном порядке. Проверяются недостача и устаревшие остатки.
- Успешный аудит откладывается до afterCommit и сохраняется в REQUIRES_NEW; откат бизнес-транзакции не создаёт ложного успеха, а сбой хранилища аудита не откатывает товар.
- Функции удаления магазина в приложении нет. Каскадное удаление магазина не добавлялось: удаление через прямой JpaRepository не является интерфейсом управления магазинами.
- SQL/JPQL с пользовательскими значениями параметризованы; динамический SQL миграции использует закрытый список таблиц и проверенные имена ограничений. Импорт базы знаний ограничен фиксированным HTTPS-хостом и не следует редиректам.

## Настройки запуска

Запуск с TLS (на сервере или корректно настроенном reverse proxy):

    java -jar target/itchecksout-0.0.1-SNAPSHOT.jar --spring.profiles.active=prod

Профиль prod включает Secure-cookie и требует DB_URL, DB_USERNAME, DB_PASSWORD для заранее подготовленной MySQL-схемы; ddl-auto=validate не создаёт схему. SQL миграции ограничен текущей схемой. На локальном HTTP остаётся обычный профиль. H2 Console выключена, vaadin.productionMode=true, ошибки сервера не включают stacktrace/message.

Для приёма заказов задайте SITE_ORDER_API_KEY (случайный секрет минимум 32 символа) и app.site-order.shop-id. Ключ должен передавать backend сайта, не публичный JavaScript. Не включайте интеграцию, пока сайт не переведён на серверный прокси. Без ключа API закрыт.

Демо разрешается только явно через app.demo-login.enabled=true. Перед настройкой Telegram укажите app.telegram.shop-id; один канал не должен смешивать независимые магазины.

## Остаточные ограничения перед публикацией

Spring Boot обновлён с 3.5.7 до 3.5.16. Vaadin обновлён с 24.9.4 до последнего бесплатного 24.9.18. Проверка обновления до 24.9.26 завершилась отказом штатного license-checker: Flow 24.9.32 требует лицензию. Проверка лицензий не отключалась.

Свежие security-патчи Vaadin 24 требуют Extended Maintenance; альтернативой является отдельная миграция на Vaadin 25 / Spring Boot 4 / Java 21. Это остаётся блокером для утверждения о полностью поддерживаемом production-стеке.

Это аудит исходного кода и автоматизированных проверок, а не внешний penetration test и не сертификация. TLS, права файлов БД/бэкапов/секретов, firewall, мониторинг и восстановление резервной копии должны быть проверены на целевом сервере. Нагрузочный тест и полный анализ CVE всех транзитивных зависимостей не заменяются этой проверкой.

Источники: https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html ; https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html ; https://vaadin.com/forum/offline-key-does-not-provide-access-to-flow-24-9-25-in-azure-devops-pipeline/179715 ; https://vaadin.com/security/advisory-2026-10-23-2
## Дополнительные проверки

Автоматизированные сценарии покрывают чужие ID в продаже/поставке/инвентаризации, запрет чужого аргумента Shop, запрет неограниченного Query-by-Example, rollback партии при ошибке второй строки, rollback остатков при отказе сохранения продажи, разделение ролей на HTTP-маршрутах, CSRF для браузерного POST, ключ сайта при наличии admin-cookie, nullable системные логи, отсутствие успешного аудита после rollback, пакетную загрузку рекомендаций для 20 товаров (не более 4 SQL-запросов).

Остаточные операционные требования: задать rate limits для логина и интеграции на reverse proxy; проверить MySQL-профиль и миграцию на staging-копии целевой БД; проверить права доступа к локальным .env, data, backups и logs. Нельзя объявлять пройденным тест MySQL по результатам H2.
## Повторный аудит после ночного сброса

Дополнительно исправлено:
- AuditLogRepository и ErrorLogRepository больше не наследуют полный JpaRepository: неограниченные findById/deleteById/QBE/batch-delete отсутствуют в их интерфейсе. Глобальные findAll/count доступны только SUPER_ADMIN; локальный findAllByShop проверяет и переданный магазин, и текущий контекст магазина непосредственно в JPQL. Запись системных логов без shop сохранена.
- Демо-вход очищает старые атрибуты HTTP-сессии перед сохранением нового SecurityContext и меняет ID сессии. Обычный вход уже использует newSession.
- ShopRepositoryBase.findAllById выполняет один параметризованный IN-запрос с обязательным shop-предикатом вместо запроса на каждый ID. Добавлена проверка смешанного списка своих и чужих ID.
- Добавлен тест отказа обычному ADMIN в глобальном чтении журналов. Предыдущий тест глобальных системных логов теперь явно использует роль SUPER_ADMIN.

Повторно просмотрены все интерфейсы репозиториев, SecurityConfig, ManagedUserDetailsManager, ShopEntityListener, SecurityUtils, основные операции Sales/Supply/Inventory/Delivery, сервисы управления учетными записями, API сайта, обработчик ошибок, настройки production и экспорты. DeliveryItemRepository отсутствует. Удаления Shop через сервис/интерфейс нет; добавлять разрушительную операцию удаления в рамках аудита не требуется. User/Shop/RoleSettings и маркер импорта являются специальными репозиториями, а не общими магазинными таблицами; глобальные операции управления пользователями защищены SuperAdminService.

Не найдено отладочных System.out/System.err. printStackTrace(PrintWriter) в ErrorLogService оставлен: он сериализует исключение в ErrorLog, а не отправляет пользователю. Демо-данные оставлены только в явно выделенных сервисах демо.

Перепроверен CVE-2026-120326 (опубликован 10 ноября): https://vaadin.com/security/cve-2026-120326 . В текущих экспортерах используются фиксированные имена файлов, заданные приложением, а не имена загруженных пользователем файлов. По условиям advisory этот сценарий не затронут. Это не отменяет требования перейти на поддерживаемую и обновляемую версию Vaadin.

Ограничения выпуска сохраняются: тесты выполняются на H2, не на целевой MySQL; не проведены внешний pentest, нагрузочный тест и полный автоматический SCA всех транзитивных зависимостей. Для MySQL необходимо настроить внешний механизм резервного копирования: встроенный BackupService поддерживает только H2. Для публичного запуска также нужны TLS, секреты интеграции, ограничения частоты запросов и проверка восстановления резервной копии на целевом сервере.
